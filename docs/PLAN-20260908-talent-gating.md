## 1. 游戏实机证据（vision-ref/game-ui 建档 03 + 总览）

| 事实 | 证据 |
|---|---|
| 天赋阵列 = 节点矩阵，**四阶段列标题 = MAX RANK 3 / 6 / 9 / 技能专精** | 建档 03 中央布局 |
| 节点带 1/2/3 斜杠级标（系列等级标记），顶行 4 黄圆、支线 3/2 节点、βγ 绿方组 | 建档 03 节点矩阵 |

**推论（草案假设，需标注不确定性）**：
- H1：矩阵**列解锁以技能 RANK 里程碑为准**（列 1=技能 RANK 3、列 2=RANK 6、列 3=RANK 9、列 4=专精开启）。
- H2：列内「精英化绿大圆」= 精英化 n 段对应的精英化节点（精 1~4 各激活一列一个节点），即精英化影响的是节点数值/上限而非列解锁。
- H3：单节点 1/2/3 级标 = 节点自身升级档（非整列解锁条件）。

## 2. 网页模型 vs 游戏机制的差距

网页简化「天赋一 max 3 / 天赋二 max 2」→ 游戏内是 ~20 节点矩阵按列解锁：
- **每干员矩阵布局不同**（顶行 4 + 支线 3/2 + βγ 组 + 底 3 + 精 4），干员间节点数/支线结构不一致；
- 网页"档"与游戏"列/节点/级标"无公开一一对应数据（森空岛 API 指纹反爬、bwiki 无终末地站、yituliu 数据不全）；
- 技能 RANK 与网页天赋档的换算无官方口径。

**结论：当前数据不足以做准确的硬锁映射。** 硬锁错配比自由点击危害更大（用户练度记到"错档"且无法表达真实状态）。

## 3. 候选方案（交用户拍板）

### 方案 A（推荐）：自由点击 + 软提示 + 数据预留
1. 保持现有自由点击（不改数据语义）；
2. 天赋行 title 补说明：「游戏内天赋阵列按技能 RANK 段解锁节点；网页档位为简化手记」；
3. ops-full.json 干员数据预留 gate 字段（talentGate: [{max, unlock}] | null），有数据时 UI 自动显示解锁条件小字（如「RANK 6 解锁」）；
4. 将来数据齐全（含每干员矩阵结构）后无缝切硬锁，无需迁移旧档。

### 方案 B（试行硬锁候选规则，可回退）
按 H1 近似映射（注意：属推断，非官方数据）：

| 档位 | 解锁条件（候选） |
|---|---|
| 天赋一 档 1 | 任意技能 RANK ≥ 3 |
| 天赋一 档 2 | 任意技能 RANK ≥ 6 |
| 天赋一 档 3 | 任意技能 RANK ≥ 9 |
| 天赋二 档 1 | 任意技能 RANK ≥ 6 |
| 天赋二 档 2 | 任意技能 RANK ≥ 9 |

- UI：未达条件档位灰锁 + tooltip 提示达标进度；
- 数据不迁移；开关可一键关（config）；
- 风险：规则为推断，若与游戏实际不符会限制记录。

### 方案 C：数据齐全后统一做（先挂起）
暂不动 UI；列入数据挖掘任务（需要森空岛页面级采集或人工补录），完成后按真实解锁表实现。

## 4. 我的建议

**方案 A**。理由：①真实机制（RANK 段列解锁 + 精英化节点 + 级标）与网页简化档位之间缺映射数据，B 的规则是推断、错锁成本高；②A 不阻塞任何现有使用，预留 gate 字段后将来升级零迁移；③软提示把"这是简化手记"说清楚，避免用户误以为网页=游戏机制。
